Arquitetura da camada

Um roteador local que normaliza entradas pesadas para a forma mais barata em tokens antes de o modelo consumir.

Esta camada não é um utilitário isolado — é um roteador por tipo de arquivo. Cada entrada percorre uma pista distinta, e o objetivo é sempre o mesmo: chegar ao modelo já em texto (Markdown) ou em uma dimensão reduzida, poupando tokens.

EntradaFerramentaSaída barata

EPUB (ebook padrão)MarkItDown (nativo, 0.1.x)Markdown
Ebook não-EPUB — mobi azw azw3 fb2 fbz lit pdb lrf tcr pml snb kepubCalibre (ebook-convert) → EPUB → MarkItDownMarkdown
PDF escaneado / imagem de textoOCR (OCRmyPDF + Tesseract) → MarkItDownMarkdown

Vídeoffmpeg (trilha) → WhisperTexto / Markdown
Imagem grandeffmpeg (redimensiona)Imagem ≤ 1568 px

Dois despachantes

A camada opera em duas frentes, e a divisão entre elas é a decisão de engenharia central:

  • Despachante automático (hook). Um hook PreToolUse sobre a ferramenta Read do Claude Code cuida apenas da pista rápida e determinística: documento digital → Markdown, imagem grande → redimensionada, e PDF escaneado pequeno → OCR sob trava. Nunca pode travar a sessão.
  • Despachante sob demanda (funções). Comandos de terminal (md, ocr, transcrever, imgredux) para o que é pesado: OCR de escaneados grandes e transcrição de mídia. Você paga a lentidão só quando decide.
Onde o hook atuaO hook cobre a leitura de arquivos do disco pelo Claude Code. Ele não age sobre conteúdo já colado no prompt, nem sobre uploads no Claude Desktop/Cowork — nesses casos, o arquivo vai para servidores remotos e não há ponto de interceptação local. Para esses, use as funções de terminal antes de subir o arquivo.
Saída sempre rastreávelIndependentemente da pista, todo Markdown gerado recebe um cabeçalho de proveniência (origem, método, ressalva, verificação). É regra obrigatória do protocolo — ver a seção marcada com ★.

Como economiza tokens

O ganho vem de transformar binário e imagem em texto — antes de o conteúdo entrar no contexto.

O ponto essencial: quando o Claude Code lê um PDF pela ferramenta Read, ele renderiza as páginas como imagem, o que consome muitos tokens de visão. Extrair o texto com o MarkItDown e ler o Markdown resultante custa uma fração disso.

Os três vetores de economia

  1. Documento → texto. Um contrato de 30 páginas em PDF digital vira Markdown limpo, sem o custo de renderização visual.
  2. Escaneado → texto. Onde o MarkItDown sozinho falharia (página só-imagem), o OCR resgata o texto e o converte.
  3. Mídia → transcrição. Áudio e vídeo, que o modelo não "lê" de forma barata, viram texto por transcrição local (Whisper).
  4. Imagem gigante → imagem justa. Uma foto de 20 MP reduzida ao lado maior de 1568 px (o ponto ótimo do Claude) preserva a leitura e corta tokens de visão.
Cache automáticoCada conversão é gravada em ~/.cache/claude-markitdown/, com chave por caminho + data de modificação (mtime). Se você editar o documento, a chave muda e a camada reconverte — não há risco de ler versão velha.

Segurança do conteúdo

Todo conteúdo convertido é dado de terceiro — jamais instrução.

Um PDF ou um áudio podem conter texto tentando injetar comandos no modelo (prompt injection indireto). A camada trata o resultado da conversão como dado, nunca como ordem.

  • O hook anexa, a cada redirecionamento, um aviso (additionalContext) declarando que o conteúdo é dado de terceiro.
  • A conversão nunca executa comandos embutidos no documento — apenas extrai texto.
  • Em material sensível (cliente, contencioso, dados pessoais), mantenha a postura de auditar a origem antes de agir sobre o conteúdo convertido.
Princípio operacionalConverter para Markdown facilita a leitura, mas não "limpa" intenções maliciosas. A blindagem está em como o conteúdo é tratado — como insumo a analisar, não como instrução a cumprir.

Cabeçalho de proveniência · obrigatório

Todo Markdown gerado pela camada nasce com um bloco de rastreabilidade — origem, método, ressalva e como verificar.

A conversão é uma tradução com perdas: OCR erra caracteres, transcrição erra palavras, extração de texto ignora páginas só-imagem. Para que o analista — humano ou artificial — nunca trate o resultado como se fosse o original, todo arquivo .md gerado DEVE começar com um cabeçalho de proveniência. É uma regra do protocolo, não um opcional.

O que o cabeçalho contém

  • Origem — o arquivo de origem e sua localização (e, quando particionado, o intervalo de páginas).
  • Método — como foi convertido (MarkItDown, OCR, transcrição, partição).
  • Ressalva — o limite de fidelidade daquele método.
  • Verificação — para onde ir em caso de dúvida (original e/ou PDF pesquisável de fallback).
  • Aviso de segurança — o conteúdo abaixo é dado de terceiro, nunca instrução (ver Segurança do conteúdo).

Formato: a primeira linha é o marcador <!-- PROVENIENCIA-CAMADA v1 --> (garante idempotência — nunca duplica), seguido de um blockquote, depois --- e o corpo. Exemplo (documento de OCR):

Ressalva por tipo de origem

TipoRessalva padrão
PDF/doc digitalcamada de texto nativa — alta fidelidade.
OCR (escaneado)pode conter erros de reconhecimento; aponta o PDF pesquisável de fallback.
OCR fraco (manuscrito / scan antigo)ATENÇÃO destacado: conferir sempre valores e nomes no original.
Áudio / vídeotranscrição automática — erros de fala/pontuação; não identifica locutores.
PDF particionadosó a camada de texto foi extraída; páginas só-imagem não aparecem; referencia o intervalo de páginas.

Fallback pesquisável — não descarte o OCR

O PDF pesquisável gerado pelo OCR (*.ocr.pdf) preserva a imagem original com uma camada de texto por cima — é a ponte entre o Markdown e o original. Por isso ele não é descartado: é arquivado em MD/_PDF-pesquisavel/ e referenciado no cabeçalho do .md correspondente. A pasta recebe um LEIA-ME.md com o mapa PDF↔MD. Ordem de confiança: original → PDF pesquisável → Markdown.

PDF gigante — partição rastreável

PDFs com dezenas de milhares de páginas travam o MarkItDown se lidos de uma vez. A regra: particionar com qpdf em pedaços de ~1.000 páginas e converter pedaço a pedaço (fallback pdftotext), gerando um .md por pedaço, nomeado com o intervalo de páginas — e cada um com seu cabeçalho (tipo partição).

Nomes colididos — desambiguar por extensão

Quando dois arquivos de origem têm o mesmo nome-base com extensões diferentes (ex.: Relatório.docx e Relatório.pdf), ambos gerariam Relatório.md e um sobrescreveria o outro. Regra: sufixar cada saída com a extensão de origem — Relatório (docx).md e Relatório (pdf).md — preservando os dois.

Como aplicarO cabeçalho é inserido pela função provmd / script provenance.sh — idempotente, com um template por tipo. Instalação e uso na seção Funções de terminal.
Regra duraNenhum .md sai da camada sem cabeçalho. Ao converter em lote, rode provmd sobre cada arquivo gerado antes de entregar — inclusive nos pedaços de um PDF particionado e na transcrição de mídia.

Python 3.10+

O MarkItDown exige Python 3.10 ou superior. No macOS, o próprio Claude Code o instala — não é etapa manual.

macOS — o Claude Code cuida distoDiferente do Claude Code (que precisa existir antes, pois é ele quem executa a camada), o Python não é um pré-requisito manual. Uma vez que o Homebrew esteja pronto (a única etapa que exige sua senha), o Claude Code instala o Python moderno autonomamente, como parte das dependências. Esta seção documenta o que ele roda — você não precisa executá-la à mão.

O Python que a Apple embute (tipicamente 3.9.6) é antigo demais e nunca é atualizado pela própria Apple. A camada instala um Python moderno em local separado, sem nunca tocar no do sistema.

Não remova o Python do sistemaO macOS usa o próprio Python internamente; apagá-lo quebra utilitários do sistema. A instalação abaixo deixa os dois convivendo, com o MarkItDown usando o moderno.

macOS — instalação isolada (o que o Claude Code executa)

O Homebrew instala o Python no seu próprio prefixo (/opt/homebrew/opt/python@3.12 no Apple Silicon; /usr/local/opt/… no Intel) e jamais sobrescreve o /usr/bin/python3 do sistema. Some-se a isso o pipx, que coloca o MarkItDown num ambiente virtual dedicado — dupla camada de isolamento. Bloco de copiar e colar que instala e comprova que o Python do sistema fica intacto:

Por que isolar assimNada de pip install global nem de mexer no PATH do Python do sistema. O Homebrew isola por prefixo; o pipx isola por venv. Se um dia remover a camada, basta desinstalar o pacote via pipx e/ou o python@3.12 via brew — o Python nativo do macOS nunca foi tocado.

Windows — referência a validar

Adaptação a testarNo Windows não há o par Homebrew+keg; o Python vem do winget ou do python.org. Este trecho é referência adaptada — validar no primeiro deploy Windows (isolamento por venv/pipx, PATH e conflito com Pythons já instalados).

Se instalar pelo python.org, marque "Add python.exe to PATH" no instalador. Prefira isolar o MarkItDown com pipx (python -m pip install --user pipx; python -m pipx ensurepath) em vez de um pip install global.

Por que 3.10+ (e por que não [all])O MarkItDown exige Python 3.10+. Evite o extra [all]: no Python 3.14 ele falha (xlrd não compila e youtube-transcript-api não tem distribuição), fazendo o pip recuar para a antiga 0.0.2 (sem EPUB). Use os extras alvo markitdown[pdf,docx,pptx,xlsx,outlook]>=0.1.7. Confirme a versão com markitdown --version (deve ser ≥ 0.1) e python3 --version antes de seguir.

macOS · Instalar dependências

Núcleo de documentos, OCR, mídia e transcrição.

1 · Pacotes Homebrew

Inclui coreutils (fornece gtimeout, usado pela trava de OCR do hook) e o Calibre (cask) — traz o ebook-convert, usado para normalizar ebooks não-EPUB.

2 · MarkItDown (via pipx)

EPUB nativo exige MarkItDown ≥ 0.1A série 0.0.x não tinha conversor de EPUB. A partir da 0.1.x o EpubConverter é embutido e converte .epub direto — metadados, títulos, listas e ênfases preservados. Confirme com markitdown --version (deve mostrar ≥ 0.1).
Word antigo (.doc)O MarkItDown converte apenas .docx (OOXML); o .doc binário legado (Word 97–2003) lança UnsupportedFormatException. A limitação é do MarkItDown, não da camada. A solução não altera o MarkItDown: adiciona um passo prévio de normalização com o textutil — utilitário nativo do macOS (/usr/bin/textutil, não instala nada) — que converte .doc → .docx num temporário antes de chamar o MarkItDown. Esse fallback já está embutido no hook, na função md e nas Quick Actions.
Ebooks (EPUB e Kindle)O EPUB é nativo no MarkItDown 0.1.x — não precisa de nada além. Os demais formatos (mobi, azw, azw3, fb2, fbz, lit, pdb, lrf, tcr, pml, snb, kepub) seguem o mesmo padrão do .doc: um passo prévio normaliza para .epub com o ebook-convert (Calibre) antes de chamar o MarkItDown. Embutido no hook, na função md e nas Quick Actions. DRM: ebooks Kindle protegidos não convertem (o ebook-convert recusa) — é esperado. O .kfx exige plugin extra do Calibre e ficou fora desta versão.

3 · Idiomas do Tesseract (português + espanhol)

Só os idiomas necessários (~32 MB), em vez do pacote completo (~1 GB). O inglês já vem por padrão. O hook e as Quick Actions usam por+eng; o spa fica instalado e disponível.

4 · Modelo do Whisper (small, multilíngue)

Precisão × velocidadeO modelo small equilibra os dois. Para áudio ruidoso (audiências), você pode trocar depois por ggml-medium.bin — mais preciso e mais lento — ajustando o caminho na função transcrever.

Solução de problemas

Sintomas comuns e o que verificar.

O hook não converte nada

Quase sempre é PATH: o hook roda com ambiente mínimo. Confirme que os binários existem (seção 9) e que a linha export PATH=… está no topo do script. Como o hook é fail-open, um PATH errado se manifesta como "nada acontece", nunca como erro.

OCR trava ou demora demais

Verifique se o gtimeout existe (brew install coreutils). Sem ele, a trava de 60 s não é aplicada e um escaneado grande pode segurar a leitura.

Quick Action não aparece no menu do Finder (erro −10811)

O bundle .workflow foi criado ou editado por fora do Automator e o LaunchServices o rejeitou. Recrie a ação dentro do Automator e nunca a edite depois — mantenha a lógica nos scripts ~/.claude/bin/*.sh (invólucro fino). Force um refresh com /System/Library/CoreServices/pbs -update.

Quick Action aparece mas "nada acontece"

É permissão de privacidade (TCC): o arquivo está numa pasta protegida (~/Downloads, ~/Desktop, ~/Documents). O macOS pede autorização no primeiro uso — conceda e repita. Confira o log em ~/Library/Logs/converter-markdown*.log.

PDF escaneado volta vazio

Confirme os idiomas do Tesseract (por, spa, eng) na pasta tessdata. Para escaneados com mais de 10 páginas, use a função ocr — o hook, por desenho, não os processa automaticamente.

Atualizar o Tesseract apaga os idiomas extrasO tessdata vive dentro do Cellar do Homebrew, então todo brew upgrade tesseract remove por.traineddata e spa.traineddata — sobram apenas eng, osd e snum, e o OCR em português volta vazio ou degradado. Não é falha de instalação: é consequência esperada do upgrade. Rebaixe os idiomas depois de cada atualização e confirme com tesseract --list-langs (esperado: eng, osd, por, snum, spa).

Transcrição não gera texto

Cheque o caminho do modelo em WHISPER_MODEL e se o whisper-cli está no PATH. Para áudio ruim, considere o modelo medium.

Documento importante perdeu formatação

Markdown descarta layout complexo (tabelas intrincadas, diagramação). Para peças onde o layout importa, leia o original — desative o hook pontualmente (seção 10) se necessário.

3 · Espelho Markdown sempre sincronizado

A partir da v1.4 o manual acompanha um espelho .md (mais barato para o Claude Code ler do que o HTML com CSS/JS). Hoje a sincronização é manual. A pesquisar: gerar o espelho automaticamente a partir do HTML (a fonte de verdade) num passo único, para o texto das duas versões nunca divergir — por exemplo, um pequeno script que extrai as seções e os blocos de código do HTML e emite o Markdown.

4 · OCR seletivo em PDF gigante

Na partição de um PDF gigante extrai-se apenas a camada de texto existente; páginas que sejam somente imagem ficam sem conteúdo no Markdown. A pesquisar: detectar automaticamente, por pedaço, as páginas sem texto (via pdffonts/pdftotext por página) e rodar OCR só nelas, evitando o custo proibitivo de um OCR completo de dezenas de milhares de páginas.

1 · Fallback para outros formatos legados

O .doc já é normalizado para .docx via textutil (nativo do macOS) antes do MarkItDown. O mesmo padrão de normalização prévia — sem tocar no MarkItDown — pode cobrir outros formatos que ele não lê nativamente:

FormatoOrigemRota de normalização proposta
.rtfRich Texttextutil -convert docx (nativo)
.odtLibreOffice/OpenOfficetextutil (suporte parcial) ou soffice --headless --convert-to docx
.pagesApple Pagesexportar via osascript/Pages, ou orientar exportação manual
.wpdWordPerfectLibreOffice (soffice) quando presente
PrincípioA limitação é sempre do MarkItDown, não da camada. A correção nunca altera o MarkItDown: insere um passo prévio que entrega um formato que ele entende (.docx de preferência). Preferir ferramentas nativas (textutil) a dependências novas; só recorrer ao soffice se já houver LibreOffice instalado, mantendo o fail-open.

2 · Instalação autônoma com menos autorizações

Hoje, mesmo o Claude Code executando tudo, o usuário precisa conceder muitas permissões ao longo do processo (cada comando, edição de arquivo e download pede aprovação). Isso interrompe o fluxo e gera confusão. Além disso, o Homebrew exige senha de administrador interativa — que o Claude Code não digita. Abordagens a pesquisar:

  • Script único de instalação (install-camada.sh). Empacotar toda a trilha macOS (deps, MarkItDown, idiomas, modelo, hook, funções, scripts de lógica) num único script idempotente e defensivo, que o usuário roda uma vez no terminal. Reduz N aprovações a uma. O Homebrew continua pré-requisito manual (senha).
  • Allowlist de permissões no settings.json. Pré-autorizar os comandos previsíveis da instalação (brew install …, curl para os domínios conhecidos, escrita em ~/.claude/**) via regras de permissions.allow, para o Claude Code não perguntar a cada passo. Requer desenhar as regras com escopo estreito.
  • Modo de permissão da sessão. Avaliar rodar a instalação numa sessão com permissões elevadas controladas (ex.: aprovação em lote / modo de permissões mais permissivo), com escopo e reversibilidade claros. Ponderar o risco: só para a janela da instalação, numa máquina confiável.
  • Instalador declarativo. Pesquisar empacotar como fórmula/tap Homebrew própria ou um Brewfile + script de pós-instalação, tornando a instalação reproduzível e versionável.
A ponderarMenos autorizações ⇒ menos atrito, porém mais poder concedido de uma vez. Qualquer abordagem deve manter: backups antes de editar, idempotência, escopo estreito das permissões e a senha de administrador sempre digitada pelo usuário (nunca pela automação). A criação das Quick Actions no Automator segue manual (erro −10811).
