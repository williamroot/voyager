01Por que este modelo existe

O acervo tem milhões de processos e centenas de milhares de autos baixados (644k+ documentos classificados). Extrair metadados deles com API paga é caro e vaza dado; com modelo local genérico é lento (o protótipo com gpt-oss:20b levava 30–60s/processo) e erra. A resposta: destilar o conhecimento de oráculos e regras determinísticas num modelo pequeno, rápido e preciso, que roda em GPU barata.

Princípio 1

Zero-erro operacional

O modelo abstém ("null") em vez de chutar. Conflito entre fontes → abstém. Precisão sobre o que é emitido > cobertura. Nada gravado é chute.

Princípio 2

Falcon só no treino

O oráculo (Falcon/Juriscope) rotula dados de treino e mede gates. Em produção o modelo opera só com os autos — sem dependência externa.

Princípio 3

LLM aponta, código decide

Saída constrangida por gramática (GBNF). Merge de entidades, saldo e agregações são determinísticos — o LLM nunca faz aritmética nem funde pessoas.

02Arquitetura do pipeline

Especialistas por tier de dificuldade, não um clone por campo. Regex resolve o que é mecânico; o 7B entra só onde há linguagem de verdade — condicionado ao tipo de documento.

autos (PDFs) ──▶ doc_classificador (23 classes; tier-1 nome + tier-2 conteúdo; 644k+ docs) │ ├── OFICIO_REQUISITORIO ─▶ beneficiário, valor individual, natureza, vara, datas ├── PLANILHA_CALCULO ────▶ valores calculados por parte, data-base ├── PROCURACAO / DOC_PESSOAL ─▶ partes {nome, cpf, papel} ├── CESSAO_CREDITO ──────▶ cedente ↔ cessionário, % / valor ├── HABILITACAO / CERT_OBITO ─▶ falecido, herdeiros[] ├── ALVARA / PAGTO_COMPROVANTE ─▶ "já recebeu": beneficiário, valor pago, data ├── SENTENCA / DECISAO ──▶ juiz POR decisão, vara/comarca, data, desfecho └── ACORDAO ─────────────▶ relator, órgão julgador, desfecho recursal │ extrator 7B (1 documento → registros JSON, grammar GBNF, temp 0) │ merger determinístico (ficha_parte.py — 24 testes) │ CPF = chave forte · fuzzy c/ guardas · espólio LIGADO │ alvará nunca cria parte · conflito → abstém ▼ FICHA DA PARTE (ledger) CONTEXTO JURIMETRIA nome canônico + CPF + papel vara / comarca / grau valor a receber (parcela DELA) juízes por decisão assinada recebido[] {valor, data, alvará} relator + câmara/turma saldo = DERIVADO (nunca extraído) desfecho por grau + datas-chave eventos: cessão, óbito, habilitação advogados + OAB

03Etapas & métricas — a história completa

Cada etapa com o número que a justificou. Nada aqui é estimativa retroativa — são os resultados dos gates da época.

ETAPA 0 · jul/2026
Protótipo RAG (o que industrializamos)
Extração live por RAG (hybrid search FTS+pgvector+RRF+rerank → top-8 chunks → gpt-oss:20b). Funcionava, mas 30–60s/processo (reasoning-model) e sem persistência. Provou o mecanismo; inviável pra volume.
latência 30–60s/procmodelo 20B reasoning
ETAPA 1 · jul/2026
Régua de avaliação (dataset Falcon)
Antes de treinar, medir: dataset de eval cruzando extrações vs oráculo Falcon por numero_autos. Achado-chave da observabilidade: ~90% do erro de extração era do LLM, não do retrieval — o lever era o modelo, não a busca. E: ente_devedor via LLM ~96,6% (melhor que o próprio Falcon no TJSP).
erro: 90% LLM / 10% retrievalente-LLM 96,6%
ETAPA 2 · 27/jul/2026
Dataset v1 — destilação triangulada (por-processo)
Gerador streaming com rótulo por triangulação de concordância: só vira ouro quando ≥2 fontes independentes concordam (Falcon∩texto, regex e-SAJ determinística, LLM∩Falcon; ente via LLM-solo alta confiança). Divergência → fila κ humana. Split por hash de CNJ (train/dev/test sem vazamento). Lição aprendida: estratificar TJSP≤50% derrubou o yield de 58%→2% — revertido pra distribuição natural.
N=8000 → 10.850 ouroente 4.188 · partes 2.225 · natureza 2.011 · cessão 1.905 · valor 52162 MB
ETAPA 3 · 28/jul/2026
Treino v1 — QLoRA na RTX 3090 (~10,4h)
Qwen2.5-7B-Instruct, 4-bit nf4, LoRA r=32/α=32 (80,7M parâmetros treináveis = 1,05%), maxseq 4096 (0 truncados), bs1×accum16, lr 2e-4 cosine, 3 épocas, gradient checkpointing. Stack: transformers 4.46 + peft 0.19 + bitsandbytes 0.50 + trl 0.12 (Unsloth abandonado — conflito de versões). Best-model por dev-loss. Incidente corrigido no meio: OOM no eval (bs=2→1 + subset 400 + exclusão de 12 exemplos all-masked que davam loss NaN).
train loss 0,53 → 0,158dev loss 0,093 → 0,073sem overfitVRAM ~19,8GB

04Ficha da Parte — o ciclo v2 (versão atual, em treino)

Reformulação completa do problema "partes": de lista one-shot por processo para extração POR-DOCUMENTO + merge determinístico. Meta: a ficha completa de cada parte — papel, CPF, valor a receber, quanto já recebeu — mais a camada de jurimetria (juiz por decisão, vara, relator, desfecho).

F0 · 28/jul
Classe ALVARA — o "já recebeu" estava invisível

F3 · 28/jul
Merger/Ledger determinístico — 24/24 testes
Camada que transforma registros por-documento em fichas (acervo/ficha_parte.py). Regras de zero-erro: CPF (só dígitos) = chave forte de merge; CPF mascarado do e-SAJ não conta; fuzzy conservador com guardas (FILHO/JR/NETO assimétrico nunca mescla; match ambíguo não mescla e flaga); espólio vira entidade ligada à pessoa; alvará nunca cria parte (órfão flagado); saldo em Decimal sempre derivado e só com os dois lados; conflito de papel → DESCONHECIDO (abstém).

Colisão de split v1×v2: zero. Guard all-masked removeu 3.227 exemplos >4096 tokens (viés contra docs longos — registrado como risco).

F2b · EM CURSO — ETA 29/jul à tarde
Treino v2 rodando na RTX 3090
Receita idêntica à v1, exceto 2 épocas (amostras/época ~2× o v1). ~1.786 steps totais. GPU 100%, VRAM 19,7GB, primeira loss 0,3965. Critérios de promoção do gate: (a) partes: F1 de entidade pós-canonicalização ≥0,75; (b) retenção v1: macro ≥85; (c) falsa-abstenção ≤5%; (d) checkpoint κ humano em amostra de fichas completas antes de qualquer deploy.

06Como rodar no Docker

Duas rotas. A recomendada é llama.cpp server, porque aceita as gramáticas GBNF por request — exatamente o modo em que o modelo foi validado. Requisitos: ~6GB VRAM (qualquer RTX 3060+) ou CPU (mais lento).

Rota A — llama.cpp server + grammar por request (recomendada)

# 1. suba o server com o GGUF (ajuste o caminho do volume pro seu host)
docker run -d --name extrator --gpus all -p 8080:8080 \
  -v /mnt/nas-data/voyager-train:/train \
  ghcr.io/ggml-org/llama.cpp:server-cuda \
  -m /train/out/precatorio-extrator-q4_k_m.gguf \
  -c 4096 -ngl 99 --host 0.0.0.0 --port 8080

# (sem GPU: troque a imagem por ghcr.io/ggml-org/llama.cpp:server e remova --gpus/-ngl)

# 2. extraia — grammar da tarefa no corpo do request (temp 0 SEMPRE)
GRAMMAR=$(cat /mnt/nas-data/voyager-train/grammars/v2/oficio.gbnf | jq -Rs .)
curl -s http://localhost:8080/completion -d @- <<EOF
{
  "prompt": "<|im_start|>system\nVocê extrai metadados de documentos judiciais.<|im_end|>\n<|im_start|>user\n${INSTRUCAO_DA_TAREFA}\n=== DOCUMENTO ===\n${TEXTO_DO_DOC}<|im_end|>\n<|im_start|>assistant\n",
  "temperature": 0, "n_predict": 512,
  "grammar": ${GRAMMAR}
}
EOF
Regra de ouro: uma grammar por tarefa (grammars/v2/{partes_doc,oficio,decisao,acordao,cessao,herdeiros,pagamento}.gbnf). Ela garante JSON 100% válido com enum fechado e null de abstenção — custo zero, elimina parse-error em produção.

Rota B — Ollama (mais simples; sem GBNF, usa JSON-schema)

# 1. suba o ollama e registre o modelo a partir do Modelfile
docker run -d --name ollama --gpus all -p 11434:11434 \
  -v ollama:/root/.ollama -v /mnt/nas-data/voyager-train/out:/models \
  ollama/ollama
docker exec ollama ollama create precatorio-extrator -f /models/Modelfile

# 2. chame com format=json-schema (ollama ≥0.30 constrange a saída de verdade)
curl -s http://localhost:11434/api/generate -d '{
  "model": "precatorio-extrator",
  "prompt": "<instrução da tarefa + texto do documento>",
  "format": {"type":"object","properties":{"beneficiario":{"type":["string","null"]},
             "valor_individual":{"type":["string","null"]},"data":{"type":["string","null"]}}},
  "options": {"temperature": 0, "num_ctx": 4096},
  "stream": false
}'

Empacotar pra levar (imagem autocontida)

# Dockerfile mínimo — modelo dentro da imagem (fica ~5GB; útil pra deploy em outra máquina)
FROM ghcr.io/ggml-org/llama.cpp:server-cuda
COPY precatorio-extrator-q4_k_m.gguf /model/model.gguf
COPY grammars/v2/ /model/grammars/
ENTRYPOINT ["/app/llama-server","-m","/model/model.gguf","-c","4096","-ngl","99","--host","0.0.0.0"]
Hardware mínimo

GPU 6GB+

RTX 3060 roda folgado. CPU-only funciona (~5-10× mais lento). RAM 8GB.

Parâmetros fixos

temp 0 · ctx 4096 · ChatML

O modelo foi treinado e gateado nessas condições. Não mude sem re-gatear.

Não faça

Servir sem grammar

Sem constraint a taxa de JSON inválido volta. E não use pra campos fora do treino (vai alucinar com confiança).

07Limitações conhecidas & próximo ciclo

Limite atual

partes = 54% na v1

Motivo raiz medido: cobertura documental (não formato, não capacidade). É exatamente o que a v2 em treino ataca com extração por-documento. Meta do gate: F1 entidade ≥0,75.

Limite atual

Alvará digitalizado sem OCR

171k alvarás no acervo, mas a maioria é scan com OCR só do rodapé. Quando há texto, a extração é ~perfeita. Lever do "já recebeu" em massa = fila de OCR, não regex.

Limite atual

Viés TJSP (~98%)

Camadas decisão/acórdão/pagamento são e-SAJ-only por ora. Cabeçalho PJe (TRF1+) precisa de padrões próprios na v2.1 pro modelo generalizar entre tribunais.

Registrado

Docs >4096 tokens dropados no treino

3.227 exemplos longos (acórdãos/escrituras grandes) fora do train v2 — viés conhecido. Fix futuro: janelar documentos longos no gerador preservando a evidência.

Próximo

Fila κ humana (13.470 casos)

Divergências entre fontes viram revisão humana com dupla anotação (κ≥0,7). O label humano (peso 3×) recalibra o próximo ciclo.

Próximo

Orquestrador de produção

Job que varre os docs do CNJ → extrator por doc → merger → persiste MetadadoExtraido. Só liga depois do gate v2 + κ humano (nunca direto em prod).
